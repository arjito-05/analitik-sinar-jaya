Aplikasi Flask kemudian mengambil data dari database SQLite memakai SQLAlchemy, mengolahnya dengan Pandas, dan menampilkan hasilnya dalam grafik Plotly. Halaman juga memuat skrip Bootstrap dan Plotly dari jaringan CDN. Sementara itu kode dan data demo disimpan di repositori GitHub. Dari arsitektur ini saya memetakan lima titik yang perlu diperhatikan, yaitu parameter filter pada alamat URL, akses tanpa login, skrip dari CDN, repositori yang bersifat publik, serta konfigurasi dan kredensial database. Kelima titik inilah yang menjadi dasar saya dalam mencari temuan pada slide-slide berikutnya. Penting dicatat bahwa karena dashboard hanya membaca data dan tidak memiliki formulir isian maupun login, permukaan serangannya relatif kecil dibandingkan aplikasi yang menerima banyak input dari pengguna.

## Slide 6: Temuan 1 dan 2

Temuan pertama dan kedua. Temuan pertama: dashboard terbuka tanpa autentikasi. Pada pengujian, permintaan ke halaman utama tanpa login langsung mengembalikan HTTP 200 dan menampilkan omzet sebesar Rp306,9 juta. Artinya siapa pun yang memiliki tautan dapat melihat data penjualan dan stok. Pada demo ini datanya simulasi, sehingga dampaknya rendah. Namun jika data yang ditampilkan adalah data riil, ini menjadi kebocoran informasi bisnis. Temuan kedua: header keamanan HTTP belum ada. Saya memeriksa enam header, yaitu Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Strict-Transport-Security, Referrer-Policy, dan Permissions-Policy, dan tidak ada satu pun yang terpasang. Akibatnya halaman dapat disematkan di situs lain untuk serangan clickjacking, yaitu pengguna tertipu mengklik sesuatu yang tersembunyi, dan browser tidak memiliki batasan sumber skrip yang boleh dijalankan. [Opsional untuk demonstrasi: buka tab Network pada alat pengembang browser, pilih permintaan pertama, lalu tunjukkan bagian Response Headers.]

## Slide 7: Temuan 3 dan 4

Temuan ketiga dan keempat berkaitan dengan konfigurasi. Temuan ketiga: pada bagian akhir file aplikasi tertulis debug sama dengan True. Jika aplikasi dijalankan langsung dan dapat dijangkau dari jaringan, fitur debugger milik Werkzeug dapat dimanfaatkan untuk menjalankan kode dari browser, sehingga dampak potensialnya sangat besar. Saya menguji aplikasi pada mode hosting, dan status debug bernilai False, karena blok tersebut hanya berjalan saat file dijalankan langsung. Jadi risikonya bersifat laten, tetapi praktik ini tetap tidak aman. Temuan keempat: konfigurasi database bawaan memakai pengguna root dengan kata sandi kosong. Ini lazim pada pengembangan lokal, namun jika server MySQL dapat dijangkau dari jaringan, seluruh database dapat diakses tanpa kata sandi. Nilai bawaan seperti ini tidak boleh terbawa ke lingkungan produksi. Pada hosting, aplikasi dijalankan oleh server WSGI sehingga mode debug tidak aktif. Namun jika suatu saat file dijalankan langsung pada komputer atau server yang terhubung ke jaringan, risikonya langsung menjadi nyata. Karena itu pengaturan debug sebaiknya tidak ditulis permanen di kode.

## Slide 8: Temuan 5 dan 6

Temuan kelima dan keenam. Temuan kelima: Bootstrap dan Plotly dimuat dari CDN tanpa atribut integrity, atau yang dikenal sebagai Subresource Integrity. Atribut ini berfungsi memastikan file yang diunduh browser sama persis dengan yang diharapkan. Tanpa itu, jika CDN dikompromikan, skrip berbahaya dapat berjalan di halaman dashboard. Ini termasuk risiko rantai pasok perangkat lunak. Temuan keenam: tidak ada pembatasan laju permintaan. Pada pengukuran, setiap permintaan ke dashboard memakan sekitar 160 sampai 190 milidetik dan menghasilkan respons sekitar 66 kilobita, karena aplikasi mengolah data dan merender lima grafik. Permintaan berulang dalam jumlah besar dapat membebani server hosting gratis hingga lambat atau tidak tersedia. Risikonya rendah karena aplikasi hanya membaca data, tetapi tetap perlu diantisipasi. Solusinya, selain memakai SRI atau menyimpan aset sendiri, pembatasan laju dan penyimpanan sementara hasil analisis, atau caching, dapat mengurangi beban karena perhitungan tidak perlu diulang pada setiap permintaan.

## Slide 9: Temuan 7 dan 8

Temuan ketujuh dan kedelapan. Temuan ketujuh: berkas database demo dan berkas CSV hasil analisis ikut tersimpan di repositori GitHub yang bersifat publik. Data tersebut dibangkitkan secara acak oleh skrip generate, sehingga bukan data pelanggan yang sebenarnya, dan karena itu risikonya rendah. Namun pola ini berbahaya apabila diterapkan pada data riil, karena dapat melanggar ketentuan perlindungan data pribadi sesuai Undang-Undang Nomor 27 Tahun 2022. Selain itu, skrip ekspor versi awal berpotensi menyalin tabel admin ke berkas yang dipublikasikan. Hal ini sudah saya perbaiki. Temuan kedelapan: versi paket gunicorn belum dikunci dan audit kerentanan paket belum dijalankan. Akibatnya paket yang usang atau mengandung celah dapat tidak terdeteksi. Audit ini belum saya lakukan pada analisis kali ini, sehingga saya cantumkan sebagai keterbatasan sekaligus rekomendasi.

## Slide 10: Kontrol yang sudah aman

Selain kerentanan, penting juga melaporkan apa yang sudah aman. Pertama, injeksi SQL. Saya mencoba tiga payload pada parameter filter, dan tidak ada yang berefek. Tabel produk tetap utuh berisi tujuh belas baris. Penyebabnya, kueri database bersifat tetap tanpa input pengguna, dan penyaringan data dilakukan di Pandas. Kedua, cross-site scripting. Dari empat payload yang saya coba, tidak ada yang lolos mentah ke HTML, karena Jinja2 melakukan escaping otomatis dan input tanggal serta kategori divalidasi. Ketiga, upaya mengakses file konfigurasi melalui jalur static ditolak dengan HTTP 404. Keempat, rute yang tidak dikenal dan metode yang salah menghasilkan 404 dan 405 tanpa menampilkan jejak tumpukan kode yang dapat membocorkan struktur aplikasi. Hasil ini menunjukkan bahwa keputusan desain awal, yaitu tidak menyusun kueri SQL dari input pengguna dan memakai templat yang melakukan escaping, sudah tepat. Namun hasil ini hanya berlaku untuk pengujian yang saya lakukan, bukan jaminan bahwa tidak ada celah lain.

## Slide 11: Perbaikan yang sudah diterapkan

Berikut perbaikan yang sudah saya terapkan langsung pada kode. Pertama, menambahkan header keamanan. Grafik di sebelah kiri menunjukkan peningkatan dari nol menjadi lima dari enam header, yaitu Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, dan Permissions-Policy. Header HSTS belum dipasang karena perlu diatur pada lapisan hosting. Kedua, mode debug kini dikendalikan oleh variabel lingkungan dan secara bawaan mati. Ketiga, saya menambahkan autentikasi HTTP Basic opsional yang aktif jika kredensial diatur lewat variabel lingkungan, sehingga kata sandi tidak tertulis di kode. Keempat, panjang parameter filter dibatasi empat puluh karakter. Kelima, skrip ekspor tidak lagi menyalin tabel admin dan kontak pelanggan. Hasil verifikasinya: grafik tetap tampil, lima skenario filter berjalan normal, dan tidak ada pelanggaran kebijakan keamanan konten. Sebagai catatan, CSP saya masih memakai unsafe-inline karena skrip grafik ditulis inline, dan ini menjadi rekomendasi jangka panjang. Seluruh perubahan ini sudah saya uji ulang secara fungsional agar tidak merusak fitur filter tanggal dan kategori yang sebelumnya saya perbaiki. Kode hasil perbaikan tersedia pada repositori GitHub proyek ini.

## Slide 12: Rekomendasi berdasarkan prioritas

Untuk rekomendasi, saya susun berdasarkan prioritas agar mudah ditindaklanjuti. Kategori segera: jika data yang ditampilkan adalah data riil, aktifkan autentikasi pada hosting, ganti pengguna MySQL root dengan pengguna khusus yang hanya memiliki izin baca, dan pastikan berkas database publik tidak memuat tabel admin. Kategori jangka pendek: tambahkan atribut SRI pada skrip CDN atau host aset sendiri, kunci seluruh versi dependensi lalu jalankan audit paket secara berkala, terapkan pembatasan laju atau caching hasil analisis, dan aktifkan HSTS pada hosting. Kategori jangka panjang: terapkan CSP berbasis nonce tanpa unsafe-inline, gunakan hashing kata sandi seperti bcrypt atau Argon2 apabila halaman admin dibuat, tambahkan pencatatan dan pemantauan aktivitas, serta susun kebijakan pengelolaan data pribadi. Urutan prioritas ini mempertimbangkan dampak dan kemudahan pelaksanaan. Langkah segera relatif murah karena hanya berupa pengaturan, tetapi mengurangi risiko yang terbesar.
